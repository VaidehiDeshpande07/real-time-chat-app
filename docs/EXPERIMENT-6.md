# EXPERIMENT 6: JWT Authentication and Role-Based Authorization

---

## 1. Aim
To implement secure JSON Web Token (JWT) based authentication and Role-Based Access Control (RBAC) in a Node.js/Express REST API backend for the NexTalk real-time chat application, ensuring that standard users (`USER`) and administrators (`ADMIN`) have distinct access privileges protected by custom Express middleware.

---

## 2. Theory

### 2.1 JSON Web Tokens (JWT)
A JSON Web Token is an open industry standard (RFC 7519) compact, URL-safe means of representing claims securely between two parties. A JWT consists of three parts separated by dots (`.`):
1. **Header:** Specifies the token type (`JWT`) and hashing algorithm (e.g., `HS256`).
2. **Payload:** Contains the claims (identifying data such as `userId`, `role`, and token expiration time `exp`).
3. **Signature:** Generated by taking the encoded header, encoded payload, a secret key, and hashing them using the specified algorithm (`HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)`).

### 2.2 Role-Based Access Control (RBAC)
Role-Based Access Control is an authorization mechanism that restricts system access based on the roles assigned to individual users:
* **Standard User (`USER`):** Can access personal chat feeds, send direct messages, retrieve contacts, and manage their session.
* **Administrator (`ADMIN`):** Possesses elevated privileges to inspect system telemetry, view aggregate user metrics, and access administrative dashboards.

### 2.3 Defense in Depth & Privilege Escalation Prevention
* Normal users registering via the public registration endpoint (`POST /api/users`) must **never** be permitted to assign themselves the `ADMIN` role. The server forces `role: "USER"` on creation regardless of client payload parameters.
* Admin privileges must only be provisioned through secure database seeding or explicit administrative management.

```
+----------------+          +-------------------+          +--------------------+
|  Client (App)  |          | Express Backend   |          | MongoDB Database   |
+----------------+          +-------------------+          +--------------------+
       |                              |                              |
       |  1. POST /api/auth/login     |                              |
       |     { email, password }      |                              |

       |                              |  2. Find User by Email       |

       |                              |<-----------------------------|

       |                              |                              |

       |     User Object {role}       |                              |
       |<-----------------------------|                              |
       |                              |                              |
       |  6. GET /api/users/admin     |                              |
       |     Authorization: Bearer jwt|                              |

       |<-----------------------------|                              |
```

## 4. Implementation Details

### 4.1 User Schema Update (`server/models/user.js`)
The MongoDB user schema was extended to include the `role` property with an enumerated set of allowed values and a default:
```javascript
role: {
    type: String,
    enum: ["USER", "ADMIN"],
    default: "USER"
}
```

### 4.2 Token Generation with Role Claims (`server/controllers/authController.js`)
Upon successful credential verification with `bcrypt.compare()`, the token payload incorporates both `userId` and `role`:
```javascript
const token = jwt.sign(
    { userId: user._id, role: user.role || "USER" },
    process.env.JWT_SECRET,
    { expiresIn: "1d" }
);
```
The response returns the token alongside user profile metadata (`_id`, `name`, `email`, `role`).

### 4.3 JWT Authentication Middleware (`server/middleware/authMiddleware.js`)
The `protect` middleware extracts the Bearer token from the HTTP `Authorization` header, verifies its digital signature against `JWT_SECRET`, and attaches the decoded identity and role to `req.user`:
```javascript
const decoded = jwt.verify(token, process.env.JWT_SECRET);
req.user = {
    id: decoded.userId,
    role: decoded.role || "USER"
};
```

### 4.4 Role-Based Authorization Middleware (`server/middleware/authMiddleware.js`)
The reusable `requireRole` middleware checks if `req.user.role` matches the permitted roles for the requested route:
```javascript
const requireRole = (...roles) => {
    return (req, res, next) => {
        if (!req.user || !req.user.role) {
            return res.status(401).json({
                message: "Not authorized, user information missing"
            });
        }

        if (!roles.includes(req.user.role)) {
            return res.status(403).json({
                message: "Forbidden: You do not have permission to access this resource"
            });
        }

        next();
    };
};
```

### 4.5 Admin-Only Route Demonstration (`server/routes/userRoutes.js`)
An administrative endpoint (`GET /api/users/admin`) was introduced:
```javascript
router.get("/admin", protect, requireRole("ADMIN"), getAdminData);
```
* **Unauthenticated Request:** Returns `HTTP 401 Unauthorized` ("Not authorized, token missing").
* **Authenticated standard `USER`:** Returns `HTTP 403 Forbidden` ("Forbidden: You do not have permission to access this resource").
* **Authenticated `ADMIN`:** Returns `HTTP 200 OK` with system statistics (`totalUsers`, `onlineUsers`, `adminUsers`).

## 5. Result
The JWT authentication mechanism and role-based access control were successfully built and tested. Privilege escalation during registration is blocked, standard users are restricted to standard features, and administrative endpoints are securely guarded.

## 6. Conclusion
Experiment 6 demonstrates the end-to-end integration of stateless JSON Web Token authentication combined with robust role-based authorization in Express and MongoDB. The application adheres to security best practices by strictly sanitizing registration inputs, signing claims with a server-side secret key, and enforcing fine-grained endpoint restrictions.
